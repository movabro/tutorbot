# Tutorbot 사용 방법

이 문서는 현재 구현된 `tutorbot` CLI를 기준으로 작성했습니다. 설계 문서와 달리 자동 스케줄러는 포함되어 있지 않으므로 실행할 때 CLI 명령을 직접 호출해야 합니다.

## 1. 설치

Python 3.10 이상이 필요합니다. 프로젝트 루트에서 가상환경을 만들고 패키지를 설치합니다.

```bash
cd /path/to/tutor_ws
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

`-e` 설치 후에는 `tutorbot` 명령을 사용할 수 있습니다. 설정과 데이터 경로가 현재 작업 디렉터리를 기준으로 해석되므로, 명령은 프로젝트 루트에서 실행하세요.

명령은 VS Code 통합 터미널이나 일반 Linux 터미널에서 실행하면 됩니다. 중요한 것은 `tutor_ws` 폴더에서 프로젝트 가상환경을 활성화하고 editable 설치를 마치는 것입니다. 가상환경 프롬프트에 `(.venv)`가 표시되는 것만으로는 `tutorbot` 실행 명령이 설치된 것은 아닙니다.

```bash
cd ~/Documents/tutor_ws
source .venv/bin/activate
python -m pip install -e ".[dev]"
tutorbot --help
```

`tutorbot: command not found`가 나오면 현재 활성화한 Python 환경에 패키지가 설치되지 않은 경우가 많습니다. 위의 `pip install` 명령을 프로젝트 루트에서 실행한 뒤 다시 시도하세요.

## 2. 설정

### API 키

프로젝트 루트에 `.env` 파일을 만들고 API 키를 넣습니다.

```dotenv
DYNALIST_TOKEN=Dynalist_API_token
LLM_API_KEY=Gemini_API_key
```

`.env`와 `config.toml`은 `.gitignore` 대상입니다. API 키를 코드나 문서에 넣거나 저장소에 커밋하지 마세요. 셸 환경변수에 같은 이름의 값이 이미 있으면 `.env`보다 환경변수 값이 우선합니다.

### `config.toml`

기본 설정 파일은 프로젝트 루트의 `config.toml`입니다. Dynalist 문서 ID와 사용할 환경변수 이름을 설정합니다.

```toml
timezone = "Asia/Seoul"
db_path = "data/tutorbot.sqlite3"

[dynalist]
token_env = "DYNALIST_TOKEN"

[domains.study]
enabled = true
file_ids = ["<학습 문서 ID>"]

[llm]
provider = "gemini"
api_key_env = "LLM_API_KEY"
model_smart = "<사용할 Gemini 모델>"
model_fast = "<사용할 Gemini 모델>"
requests_per_minute = 10
```

학습 문서 ID는 `[domains.study].file_ids`에 지정합니다. 현재 LLM 구현은 Gemini만 지원하며 기본 모델은 `gemini-3.5-flash-lite`입니다. `model_smart`와 `model_fast`로 모델을 변경할 수 있습니다. `[llm].requests_per_minute`는 실제 Gemini 요청 사이의 프로세스 내 제한으로, 생략하면 10 RPM(최소 6초 간격)입니다. 양의 정수만 허용되며 여러 독립 프로세스/호스트의 합산 요청률은 조정하지 않습니다. 실제 Gemini client가 처음 요청할 때 로그에 RPM 값과 프로세스 로컬 범위(다른 프로세스/호스트와 조정되지 않음)를 한 번 기록합니다. 이 값은 RPM만 제어하고 TPM·일일 할당량이나 Google이 제공하는 실제 API quota를 보장하지 않습니다. 설정값 및 태그·퀴즈·처리 제한의 전체 기본값은 프로젝트 설정 파일을 참고하세요.

다른 설정 파일을 사용하려면 각 명령 앞에 `-c`를 지정합니다.

```bash
tutorbot -c config.toml doctor
```

### 도메인 프로필 (선택)

도메인 프로필은 학습 문서 외에 업무·일상·커리어·개인 과업·개발 로그 문서를 선택적으로 사용할 수 있습니다. 각 프로필은 문서를 여러 개 지정할 수도 있지만, 기록과 피드백이 섞이지 않도록 도메인별 문서를 분리하세요.

| Dynalist 문서 | 새로 만들기 | 목적 및 처리 방식 |
|---|---:|---|
| 학습 | 아니요 | 기존 학습 목표·지식 덤프·공부 기록을 유지합니다. `[domains.study].file_ids`에 둡니다. |
| 업무 | 예 | 업무 목표, 진행, 결과를 기록합니다. 이 문서를 읽어 업무 피드백을 같은 문서에 기록합니다. |
| 일상 | 예 | 일상과 가족 관련 과거·예정 이벤트를 기록합니다. Tutorbot은 이 기록을 생산성 목표로 평가하지 않으며, 명시된 일정에 관한 피드백을 같은 문서에 기록합니다. |
| 커리어 | 예 | 커리어 방향성 관찰과 피드백을 축적하는 문서입니다. 별도의 일일 기록은 필요 없고, 설정한 업무·일상 문서를 읽어 이 문서에만 결과를 기록합니다. |
| 개인 과업 | 예 | 회사 업무와 분리된 개인 프로젝트·할 일의 상태와 진행을 관리하고 피드백을 기록합니다. |
| 개발 로그 | 선택 | Tutorbot은 최근 사용자 코멘트에 피드백을 작성하고, 실제 `run`의 실행 로그를 날짜·시간 노드로 기록합니다. 개발 로그 문서는 학습/일반 도메인 요약의 source로 사용하지 않습니다. |

개발 로그를 포함해 모든 프로필을 사용하는 경우 학습 문서를 포함해 최대 6개 문서가 사용됩니다. 도메인을 일부만 사용할 경우에는 사용할 프로필의 문서만 설정하면 됩니다. 커리어 프로필을 사용한다면 입력 출처로 선택한 업무·일상 프로필에도 문서 ID가 설정되어 있어야 합니다.

`[domains.study].file_ids`에 기존 학습 문서 ID를 지정합니다. 아래 프로필 설정은 기존 `config.toml`에 추가합니다.

```toml
[domains.work]
enabled = true
file_ids = ["<업무 문서 ID>"]
tags = ["project", "client"]

[domains.life]
enabled = true
file_ids = ["<일상 문서 ID>"]
tags = ["family", "health"]

[domains.career]
enabled = true
file_ids = ["<커리어 문서 ID>"]
tags = ["career", "direction"]
source_domains = ["work", "life"]

[domains.personal_tasks]
enabled = true
file_ids = ["<개인 과업 문서 ID>"]
tags = ["hobby", "home"]
tracking_tag = "Track"
status_nodes = ["Backlog", "InProgress", "FastTrack", "Completed", "Abandon"]

[domains.devlog]
enabled = true
file_ids = ["<개발 로그 문서 ID>"]
```

각 도메인의 입력과 피드백은 해당 프로필의 `file_ids` 문서에 한정됩니다. 커리어는 `source_domains`에 적은 도메인만 입력으로 읽으며, 위 설정에서는 업무·일상 문서만 읽고 커리어 문서에 결과를 기록합니다. 개발 로그에서는 최근 변경된 비봇 사용자 노드만 코멘트 피드백 대상으로 삼습니다. `--dry-run`은 실행 로그를 개발 로그 문서에 저장하지 않습니다. 토큰 등 비밀 값은 기존과 같이 환경 변수에서만 읽습니다.

각 도메인의 `tags` 배열에는 해당 도메인에서 참고할 태그 이름을 `#` 없이 적습니다. 이 값은 분석 프롬프트에 전달되는 참고 정보이며 문서에서 해당 태그가 있는 노드만 필터링하지는 않습니다. 기존 학습 태그는 `[tags]` 아래에서 설정합니다. 프로필별 `rules`와 `prompt`로 추가 분석 지침을 지정할 수 있고 출력 형식은 현재 `feedback_json`만 지원합니다. 개인 과업의 `tracking_tag_aliases`로 `#Track` 외에 추적 항목으로 인식할 태그를 추가할 수 있습니다.

개인 과업 문서에는 상태 노드를 정확히 `Backlog`, `InProgress`, `FastTrack`, `Completed`, `Abandon`으로 만들고, 상태 아래에 분류용 부모 노드와 실제 추적 항목을 둡니다. `#Track`은 실제 추적 항목 본문에만 붙입니다. 진행 기록은 추적 항목의 직접 자식으로 두고 `!(yyyy-mm-dd)` 날짜를 기록합니다. 노트와 자손 노드는 해당 진행 기록의 상세 내용으로 읽힙니다.

```text
Backlog
  해내고 싶은 프로젝트
    개인 포트폴리오 정리 #Track
      기존 프로젝트의 성과를 정리 !(2026-11-15)
        노트: 역할과 결과를 다시 확인함
        프로젝트 A
          담당 업무와 결과 정리
InProgress
  매주 운동하기 #Track
    첫 번째 운동 기록 !(2026-11-16)
Completed
  취미 등 하고 싶어서 해 본거
    악기 연습 시작하기 #Track
      첫 수업을 마침 !(2026-11-14)
Abandon
  중단할 개인 과업 #Track
```

`Completed` 아래의 분류 노드는 자유롭게 추가할 수 있으며, 그 아래 분류 경로가 완료 이벤트에 저장됩니다. Tutorbot은 `Backlog` 항목을 진행 기록이 있을 때 분석합니다. `Completed` 항목에는 최종 성과·회고를, `Abandon` 항목에는 중단 상태를 기록하며 일반 진행 피드백은 반복하지 않습니다. 날짜가 없거나 유효하지 않은 기록은 정성적 분석에는 포함될 수 있지만 Tutorbot은 날짜 집계용 정규화 날짜를 저장하지 않습니다. Tutorbot은 날짜 원문을 보존하고 실행 진단에 경고하며, 날짜를 추측하거나 보정하지 않습니다. 완료 이벤트는 SQLite에 저장됩니다. 처음 실행했을 때 이미 `Completed`인 항목의 실제 완료 시점은 알 수 없으므로 비워 둡니다.

1단계 구현은 도메인별 분석 피드백과 완료 이벤트 저장까지 지원합니다. 신규 통합 리포트, PDF, 텔레그램 및 슬랙 연동은 포함하지 않습니다.
설정을 저장한 뒤 기존 기본 실행 순서(§4)에 따라 `tutorbot run`을 실행하면 설정된 활성 도메인이 처리됩니다.

### 향후 피드백 규칙과 페르소나 초안

> **중요 — 미구현 제안입니다.** 아래 규칙과 설명서는 현재 동작하는 기능이 아니라 향후 구현 방향만 설명합니다. 현재 설정 로더, TOML 파서 및 스케줄러는 이 형식을 지원하지 않습니다. 이 내용을 `config.toml`에 복사하거나 실행해도 작동하지 않으며, 이를 활성화하거나 검증하는 명령도 없습니다. 기존 `[domains.*]`에 필드를 추가하면 현재 설정 검증 오류가 발생할 수도 있습니다.

- [피드백 규칙 TOML 초안](templates/feedback-rules.example.toml): 피드백 작업별 선택 노드·참조·출력, 태그와 시간 필터, 주기, 토큰 및 근거에 대한 제안입니다. 실제 문서·노드 ID와 출력 위치 등은 사용자가 결정해야 합니다.
- 페르소나 작성 템플릿: [학습](templates/personas/study.md), [업무](templates/personas/work.md), [일상](templates/personas/life.md), [커리어](templates/personas/career.md), [개인 과업](templates/personas/personal_tasks.md), [개발 로그](templates/personas/devlog.md).

#### 생각하는 방법과 설계 순서

먼저 `domain`과 피드백 작업을 구분하세요. 규칙 파일 하나에 `[[feedback_rules.tasks]]`를 여러 번 써서 서로 독립된 작업을 여럿 정의할 수 있습니다. 이 초안에서는 TOML 항목을 `feedback_rules.tasks`라고 부르며, 각 항목 하나가 목적, 소스, 결과 위치와 처리 방식을 갖춘 전체 지시 단위입니다.

| 구분 | 의미 |
|---|---|
| `domain` | `study`, `career` 같은 분류·라벨로, “이 작업은 어떤 범주에 속하는가?”에 답합니다. 소스 문서를 선택하거나 입력·출력 문서를 정하지 않습니다. |
| 피드백 작업 | `purpose`, `selection`, `references`, `output`, 처리 방식(`unit`, `schedule` 등)을 함께 정의한 작업 단위입니다. 실제 소스는 작업의 `selection`과 `references` 항목이 지정하고 결과 위치는 `output`이 지정합니다. |

예를 들어 `domain = "career"`인 작업의 목적이 업무·학습·일상 기록을 커리어 목표와 비교하는 것이라면, `selection`에는 업무·학습·일상 문서를, 문맥으로만 읽을 커리어 목표 문서는 `references`에 지정하고, 결과는 커리어 문서에 쓰도록 `output`을 지정할 수 있습니다. 소스와 결과 문서는 작업의 `domain`과 다른 범주에 속해도 됩니다. 즉, “이 작업은 어떤 범주인가?”는 `domain`으로, “어떤 소스를 쓰고 어디에 결과를 둘 것인가?”는 각 작업의 `selection`·`references`·`output`으로 정합니다.

입출력을 설계할 때 세 역할을 분리하세요.

| 구역 | 역할 | 결과에 미치는 영향 |
|---|---|---|
| `selection` | 피드백을 받을 피드백 대상 노드를 선택합니다. | 선택된 노드가 실제 피드백 대상 노드입니다. 여러 선택 소스의 결과는 합집합입니다. |
| `references` | 선택된 피드백 대상 노드를 이해하는 데 필요한 추가 문맥을 제공합니다. | 참고로 읽을 뿐, 그 자체로 피드백 대상 노드로 선택되지는 않습니다. |
| `output` | 결과를 쓸 문서와 위치를 정합니다. | 입력 문서와 다를 수 있으며, 출력 위치를 명시적으로 설계합니다. |

실무 설계는 다음 순서로 진행하는 편이 명확합니다.

1. 해결하려는 문제와 결과물을 정하고, 피드백 작업의 `id`, `purpose`, 분류용 `domain`을 구상합니다.
2. 실제 피드백 대상이 될 노드만 `selection`에 둡니다. 여러 선택 소스 문서나 소스 범위를 넣으면 결과가 합쳐지는 점을 고려하고, 피드백 대상 노드가 하나도 선택되지 않는 경우도 점검합니다.
3. 목표·기록처럼 설명에 필요한 자료는 `references`에 따로 둡니다. 참고 자료를 피드백 대상 노드처럼 오해하지 않도록 역할을 구분합니다.
4. `unit`, `schedule`, 시간대와 토큰 범위를 정하고, 결과를 어느 문서·부모에 둘지 `output`으로 설계합니다.
5. 파일 및 노드 ID, 범위, 태그, 시간 조건, 출력 권한과 페르소나 파일 경로를 확인합니다. 예시의 자리표시자는 실제 ID가 아니며, 아래 예시를 운영 설정으로 복사하거나 실행해서는 안 됩니다.

#### 피드백 작업 필드 참고표

아래 의미는 템플릿이 제안하는 의미입니다. 이 형식에 대한 구현된 스키마나 실행 동작을 뜻하지 않습니다.

| 필드 | 제안 의미와 작성 시 고려할 점 |
|---|---|
| `id` | 피드백 작업을 구별하기 위한 식별자입니다. 고유성 규칙이나 허용 문자는 정해져 있지 않습니다. |
| `purpose` | 피드백 목적과 기대 결과를 사람이 이해할 수 있게 적습니다. |
| `domain` | 피드백 작업의 분류입니다. 템플릿에는 `study`, `career` 같은 예가 있지만 허용되는 값의 전체 목록은 정해져 있지 않습니다. 입력 소스의 도메인과 같아야 한다는 뜻도 아닙니다. |
| `persona_path` | 사용할 페르소나 문서 경로의 제안입니다. 경로는 설정 파일이 놓인 디렉터리를 기준으로 한 상대 경로로 제안되어 있습니다. 자동 로딩은 구현되지 않았습니다. |
| `persona_approval` | 페르소나 적용 전 승인 정책의 제안입니다. 예시 값은 `user_approved_before_use`입니다. 승인·추천 절차는 구현되지 않았습니다. |
| `unit` | 출력 단위 제안입니다. `per_node`는 선택 노드마다 피드백 결과를 하나씩 만들고, `aggregate`는 선택 결과를 모아 피드백 결과 하나를 만드는 방식입니다. |
| `schedule` | 처리 주기 제안입니다. `each_run`은 실행마다, `daily`는 시간대 기준 현지 날짜별 처리입니다. 실제 스케줄러는 지원되지 않습니다. |
| `timezone` | `daily`의 현지 날짜를 계산할 시간대 제안입니다. 템플릿 예시는 `Asia/Seoul`입니다. 일일 실행 시각은 정해져 있지 않습니다. |
| `input_token_range` | 한 번의 호출에서 입력 토큰 수로 삼을 목표 범위입니다. 엄격한 상한이나 비용 한도가 아닙니다. |
| `output_token_range` | 한 번의 호출에서 출력 토큰 수로 삼을 목표 범위입니다. 엄격한 상한이나 비용 한도가 아닙니다. |
| `evidence` | 문서·노드 ID에 연결해 근거를 제시하고, 입력이 없거나 잘린 경우 이를 알리도록 하는 지침입니다. 출처를 검증하거나 근거의 정확성을 보증하는 기능은 아닙니다. |

페르소나 경로를 작성할 때는 설정 파일의 위치를 기준으로 상대 경로를 구상하세요. `user_approved_before_use`는 템플릿의 승인 정책 예시일 뿐이며, 승인 요청·추천·동의 저장·승인 후 적용 중 어느 절차도 현재 구현되어 있지 않습니다.

#### 선택·참조 소스 필드 참고표

아래의 소스 설정은 `[[feedback_rules.tasks.selection]]` 및 `[[feedback_rules.tasks.references]]`에 제안된 항목입니다. `context_scope`는 `selection`에만 해당합니다.

| 필드 | 적용 범위 | 제안 의미 |
|---|---|---|
| `file_id` | 선택·참조 | 읽을 Dynalist 문서의 ID입니다. 선택 소스 문서와 참조 문서는 피드백 작업의 결과 문서와 같을 수도, 다를 수도 있습니다. |
| `parent_node_id` | 선택·참조 | 범위를 펼칠 기준 노드의 ID입니다. 실제 노드 ID로 바꿔야 합니다. |
| `scope` | 선택·참조 | 기준 노드에서 읽을 범위입니다. `self`는 기준 노드 자체, `descendants`는 자손만, `self_and_descendants`는 기준 노드와 자손을 뜻합니다. |
| `context_scope` | 선택만 | 선택된 각 피드백 대상 노드에 붙일 문맥의 범위를 세밀하게 제안합니다. 예시 `self_excluding_nested_goal_subtrees`는 해당 목표 자체와 문맥은 두되, 중첩된 다른 목표 및 그 하위 트리는 제외하는 의미입니다.  `self_and_descendants`(고른 노드와 모든 하위 항목)와 `self_and_children`(고른 노드와 바로 아래 자식만)도 항목에 있습니다. |
| `tags_any` | 선택·참조 | 목록의 태그 이름 중 하나 이상에 맞는 소스를 허용하는 제안입니다. `#` 기호는 빼고 적으며 `[]`는 태그 필터를 적용하지 않는다는 뜻입니다. |
| `time` | 선택·참조 | 소스의 시간 조건입니다. 예시는 `created_last_24h`와 `fixed_context`입니다. |

제안된 필터 의미는 다음과 같습니다.

- 한 피드백 작업에 `selection` 소스가 여러 개면 각각 선택된 노드의 합집합을 피드백 대상 노드로 삼습니다. `references`는 문맥만 제공하며 피드백 대상 노드 집합에 더해지지 않습니다. 선택 결과가 비어 있으면 참고 자료가 있더라도 해당 피드백 작업을 건너뛰는 안입니다.
- `scope`는 각 소스의 `parent_node_id`를 기준으로 해석합니다. `tags_any`와 `time`은 해당 선택 또는 참조 소스 각각에 적용되며, 한 소스의 필터가 다른 소스에 전파되거나 부모 필터가 자손에게 상속되는 방식은 아닙니다. 태그 조건과 시간 조건은 같은 소스에 모두 적용하는 제안입니다.
- `tags_any = []`는 모든 태그를 허용하는 뜻으로 제안되어 있습니다. 값에서 `#`는 생략합니다. 다만 정확한 태그 파서, 경계 판정 및 대소문자 처리 방식은 정해져 있지 않습니다.
- `created_last_24h`는 실행 시각을 기준으로 생성 시각이 `[실행 시각 - 24시간, 실행 시각)`에 있는 노드를 선택하는 제안입니다. 수정만 된 노드는 새로 생성된 것으로 보지 않습니다.
- `fixed_context`는 24시간 생성 조건에 제한하지 않고 오래된 문서·노드의 현재 스냅샷을 문맥으로 읽는 제안입니다. `fixed_context`를 선택에 쓰면 나이가 오래된 대상도 후보가 될 수 있습니다.

#### 출력 단위와 주기

| 설정 | 제안 동작 |
|---|---|
| `unit = "per_node"` | 선택된 노드마다 결과 하나를 만들고 각 결과를 해당 선택 노드의 직접 자식으로 추가하는 안입니다. 템플릿의 대응 `placement` 예시는 `under_each_selected_node`입니다. |
| `unit = "aggregate"` | 선택된 노드를 모아 결과 하나를 만듭니다. 결과는 `output`에 지정한 문서의 `parent_node_id` 노드의 직접 자식으로 추가하는 안이며 대응 `placement` 예시는 `under_parent`입니다. |
| `schedule = "each_run"` | 실행할 때마다 처리하는 제안입니다. |
| `schedule = "daily"` | 지정한 시간대의 현지 날짜마다 성공을 최대 한 번 기록하는 제안입니다. 이미 지난 날짜의 실행을 나중에 보충(backfill)하지 않습니다. 시간대가 현지 날짜 경계를 결정하므로 결과에 영향을 줍니다. |

`per_node`와 `aggregate`는 `unit` 값이고 `under_each_selected_node`, `under_parent`는 `placement` 값입니다. 서로 다른 필드의 값이므로 혼동하지 마세요. 조합이나 불일치 처리를 포함한 전체 제약은 아직 형식적으로 정해져 있지 않습니다. `daily` 역시 실행 시각, 실패·재시도·동시 실행 처리까지 정의한 스케줄러가 있다는 의미가 아닙니다.

#### 출력 필드 참고표

| 필드 | 제안 의미 |
|---|---|
| `file_id` | 결과를 기록할 문서 ID입니다. 선택 소스 문서와 달라도 됩니다. 템플릿의 per-node 예시는 결과를 선택 노드의 직접 자식으로 두므로 이 필드를 생략하고, aggregate 예시는 출력 문서 ID를 지정합니다. |
| `parent_node_id` | `under_parent`일 때 결과를 직접 자식으로 추가할 부모 노드 ID입니다. |
| `placement` | 결과 배치 방식의 제안입니다. `under_each_selected_node`는 선택 노드마다 그 노드의 직접 자식으로 결과를 추가하고, `under_parent`는 `output.parent_node_id`로 지정한 부모 노드의 직접 자식으로 결과 하나를 추가합니다. |

예를 들어 지정 노드를 부모로 하는 출력 계층은 다음과 같습니다.

```text
지정 노드
  피드백 결과   ← 지정 노드의 직접 자식
같은 단계 노드 ← 지정 노드의 형제, 자식이 아님
```

같은 단계에서 뒤에 적는 노드는 형제입니다. 이 초안에는 형제 노드 출력 옵션이 없습니다. `scope`의 `descendants`는 직접 자식뿐 아니라 손자 등 모든 자손을 뜻합니다.

#### 템플릿을 바탕으로 한 설계 예시

다음 예시는 구조와 의도를 보여 주기 위한 TOML 초안이며, 구문만 놓고 보면 TOML 표기 예시입니다. 꺾쇠로 표시한 ID는 일부러 알아볼 수 있게 만든 자리표시자입니다. 이를 실제 ID로 교체해 `config.toml`에 설치하거나 실행하지 마세요. 현재 로더·파서·스케줄러는 이 기능을 지원하지 않으며, 작동하거나 검증되지 않습니다.

학습 목표를 각자 평가하는 `per_node` 제안입니다. 선택된 피드백 대상 노드는 목표이고, 공부 기록은 문맥으로만 읽습니다.

```toml
[[feedback_rules.tasks]]
id = "DESIGN_ONLY_study_goal_review"
purpose = "각 학습 목표에 대해 지식 평가와 다음 학습 제안"
domain = "study"
persona_path = "docs/templates/personas/study.md"
persona_approval = "user_approved_before_use"
unit = "per_node"
schedule = "each_run"
input_token_range = [1000, 4000]
output_token_range = [200, 700]
evidence = "전달된 목표와 기록의 문서/노드 ID를 제시하고, 없거나 잘린 내용은 표시"

[[feedback_rules.tasks.selection]]
file_id = "<DESIGN_ONLY_STUDY_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_GOAL_LIST_NODE_ID>"
scope = "descendants"
context_scope = "self_excluding_nested_goal_subtrees"
tags_any = ["목표", "goal"]
time = "fixed_context"

[[feedback_rules.tasks.references]]
file_id = "<DESIGN_ONLY_STUDY_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_STUDY_RECORDS_NODE_ID>"
scope = "descendants"
tags_any = ["공부", "study"]
time = "created_last_24h"

[feedback_rules.tasks.output]
placement = "under_each_selected_node"
```

업무·학습·일상 기록을 선택해 커리어 문맥과 대조하는 `aggregate` 제안입니다. 세 선택 소스의 결과는 합쳐지며 커리어 목표는 참고 자료이고, 출력은 커리어 문서의 지정 부모에 직접 자식 하나로 추가하는 안입니다.

```toml
[[feedback_rules.tasks]]
id = "DESIGN_ONLY_career_daily_review"
purpose = "업무·학습·일상 기록을 커리어 목표와 비교해 종합"
domain = "career"
persona_path = "docs/templates/personas/career.md"
persona_approval = "user_approved_before_use"
unit = "aggregate"
schedule = "daily"
timezone = "Asia/Seoul"
input_token_range = [2000, 8000]
output_token_range = [400, 1200]
evidence = "각 기록의 문서/노드 ID와 목표를 연결하고 근거 부족은 표시"

[[feedback_rules.tasks.selection]]
file_id = "<DESIGN_ONLY_WORK_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_WORK_RECORDS_NODE_ID>"
scope = "descendants"
tags_any = ["work", "업무"]
time = "created_last_24h"

[[feedback_rules.tasks.selection]]
file_id = "<DESIGN_ONLY_STUDY_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_STUDY_RECORDS_NODE_ID>"
scope = "descendants"
tags_any = ["공부", "study"]
time = "created_last_24h"

[[feedback_rules.tasks.selection]]
file_id = "<DESIGN_ONLY_LIFE_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_LIFE_RECORDS_NODE_ID>"
scope = "descendants"
tags_any = ["life", "일상"]
time = "created_last_24h"

[[feedback_rules.tasks.references]]
file_id = "<DESIGN_ONLY_CAREER_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_CAREER_GOALS_NODE_ID>"
scope = "self_and_descendants"
tags_any = []
time = "fixed_context"

[feedback_rules.tasks.output]
file_id = "<DESIGN_ONLY_CAREER_FILE_ID>"
parent_node_id = "<DESIGN_ONLY_CAREER_OUTPUT_PARENT_NODE_ID>"
placement = "under_parent"
```

두 예시의 TOML 모양은 별도 임시 파서에 넣어 문법을 살펴볼 수 있도록 작성한 것이지만, 이는 Tutorbot이 해당 설정을 이해하거나 검증한다는 뜻이 아닙니다. 어떠한 Tutorbot 명령도 이 초안을 활성화하거나 유효성 검사하지 않습니다. **실제 `config.toml`에 복사하거나 운영 중인 명령으로 실행하지 마세요.**

#### 아직 결정되지 않은 사항

템플릿은 제안이며 완전한 스키마 명세가 아닙니다. 다음 사항에 대해서는 필요한 답을 추측하지 말고 미결정으로 다루세요.

- 어떤 필드가 필수인지 선택인지, 생략 시 어떤 기본값을 쓸지 정해져 있지 않습니다.
- `domain`의 가능한 값 전체, 식별자 형식과 유효성 검사 규칙이 정의되어 있지 않습니다. `study`, `career` 등은 예시일 뿐입니다.
- 실제 태그 문법과 파싱, 대소문자 비교 방식은 정의되어 있지 않습니다.
- 입력·출력 토큰 목표를 초과할 때 분할, 축약, 중단 중 무엇을 할지 정해져 있지 않습니다. 따라서 이 범위를 하드 캡이나 비용 제한으로 간주하면 안 됩니다.
- 오류 처리, 재시도, 중복 및 출력 충돌 해결 정책이 정의되어 있지 않습니다.
- 실행 가능한 운영 런타임과 검증 명령은 없습니다. 현재 설정 로더, TOML 파서 및 스케줄러도 이 초안을 지원하지 않습니다.

`evidence`는 모델에 전달할 지침으로, 응답이 입력의 문서·노드 ID에 근거를 연결하고 출처 내용이 없거나 잘렸으면 이를 밝히도록 제안합니다. 이는 ID의 실제 존재나 응답의 인용을 확인하는 검증 보장이 아닙니다. 출력 가능한 근거의 품질도 입력에 좌우됩니다.

기존 도메인 프로필의 `rules`와 `prompt`는 현재 기능의 텍스트 지침이며, 기존 `tags`는 프로필에서 참고할 태그 정보이지 노드 선택 필터가 아닙니다. 여기 설명한 독립 피드백 작업, 페르소나 파일 경로, 승인 방식과 필터는 별도의 향후 제안이며 현재 규칙과 혼합해 사용할 수 없습니다.

#### 마무리 점검 및 개인정보

향후 설계안을 공유하기 전에 다음을 확인하세요.

- [ ] 각 피드백 작업의 목적과 분류를 정했으며, `domain`을 입력 문서 제한으로 오해하지 않았습니다.
- [ ] 피드백 대상 노드와 참고 문맥을 구분했고, 여러 선택 소스의 합집합 및 빈 선택 시 건너뛰는 제안을 고려했습니다.
- [ ] 각 선택·참조 소스의 문서, 부모 노드, 범위, 태그, 시간 조건을 따로 확인했습니다.
- [ ] `per_node`/`aggregate`, `each_run`/`daily`, 시간대 및 출력 배치가 의도와 일치합니다.
- [ ] 실제 문서·노드 ID와 권한을 별도로 확인했고, 모든 `DESIGN_ONLY` 값과 꺾쇠 자리표시자가 예시용임을 확인했습니다.
- [ ] 토큰 범위를 호출당 목표로 이해하고, 근거 지침을 검증 보장으로 간주하지 않았습니다.
- [ ] 이 미구현 제안을 `config.toml`에 복사하거나 실행하지 않습니다.

**개인정보 주의:** 이 설계가 향후 구현될 경우 입력 문서와 프롬프트에 포함된 개인정보 또는 민감정보가 외부 LLM API 제공자에게 전달될 수 있습니다. 설계 문서나 페르소나 초안에는 불필요한 개인정보, 실명, 비밀 값 및 자격 증명을 넣지 마세요. 실제 기능에서 `--dry-run`도 API 호출을 막지 않는다는 점을 포함해, 기존 실행 기능의 주의사항은 위 도메인 설정 설명을 따르세요.

> **다시 확인:** 이 규칙과 설명서는 미구현 설계 제안일 뿐입니다. 현재 로더·파서·스케줄러가 지원하지 않으며 `config.toml`에 복사하거나 실행해도 작동하지 않습니다. 이를 활성화하거나 검증하는 명령은 없습니다.

## 3. Dynalist 문서에 학습 내용 작성하기

### 먼저 알아둘 용어

> **문서(document)**: Dynalist에서 여는 하나의 파일입니다. 설정의 `file_ids`에 지정한 문서를 Tutorbot이 읽습니다.
>
> **노드(node)**: Dynalist 문서의 글머리표 한 줄입니다. 노드에는 본문을 쓰고, 다른 노드를 들여써서 자식 노드를 만들 수 있습니다.
>
> **자식 노드(child node)**: 다른 노드 아래로 들여쓴 글머리표입니다. 공부 기록의 예제나 근거를 나누어 적을 때 사용합니다. 자식 노드와 노트는 서로 다릅니다.
>
> **본문(content)**: 노드의 글머리표 옆에 입력하는 텍스트입니다. Tutorbot은 본문에서 학습 유형 태그를 찾습니다.
>
> **메모(note)**: 노드에 별도로 붙이는 긴 메모 영역입니다. Tutorbot은 메모 내용도 학습 기록에 포함하지만, 태그는 본문에서만 찾습니다. 날짜 표기 `!(YYYY-MM-DD)`는 본문이나 메모에 둘 수 있습니다.
>
> **태그(tag)**: `#`으로 시작하는 분류 표시입니다. 예를 들어 `#공부`는 공부 기록입니다. 태그는 본문에 쓰며, 태그만 메모에 적으면 해당 노드는 분류되지 않습니다.
>
> **토픽 태그(topic tag, 주제 태그)**: `#python`, `#rust`처럼 학습 주제를 나타내는 사용자 지정 태그입니다. 목표가 여러 개일 때 공부 기록이나 지식 덤프를 어느 목표에 연결할지 구분하는 데 씁니다. `#topic`이라는 태그를 그대로 쓰는 것이 아니라, 목표에 붙인 태그를 그대로 다시 사용합니다.

아래 예시에서 들여쓰지 않은 글머리표는 같은 단계이고, 들여쓴 글머리표는 바로 위 노드의 자식입니다. Dynalist 편집기에서 `Enter`로 새 노드를 만들고, `Tab` / `Shift+Tab`으로 들여쓰기 / 내어쓰기를 합니다. `Shift+Enter`는 노드 본문과 메모 입력을 전환합니다.

처음 작성할 때는 다음 순서로 입력하면 됩니다.

1. 설정된 Dynalist 문서를 엽니다.
2. 새 글머리표에 내용을 입력합니다. 같은 단계의 다음 노드는 `Enter`로 만듭니다.
3. 설명이나 예제를 자식 노드로 나누려면 `Tab`으로 들여씁니다. 부모 단계로 돌아가려면 `Shift+Tab`을 누릅니다.
4. 노트(메모)에 긴 설명을 쓰려면 해당 노드에서 `Shift+Enter`로 메모 입력으로 전환합니다. 다시 `Shift+Enter`를 누르면 본문 입력으로 돌아옵니다.

Dynalist의 공식 안내: [새 항목 만들기](https://help.dynalist.io/article/57-create-a-new-item), [Dynalist 기본 사용](https://help.dynalist.io/article/130-dynalist-basics), [키보드 단축키](https://help.dynalist.io/article/91-keyboard-shortcut-reference).

### 태그와 노드 구조

기본 태그는 다음과 같습니다.

| 쓰임 | 인식되는 태그 | 설명 |
|---|---|---|
| 학습 목표 | `#목표`, `#goal` | 목표와 커리큘럼 생성 |
| 지식 덤프 | `#지식덤프`, `#dump` | 이미 알고 있는 내용의 평가 |
| 공부 기록 | `#공부`, `#study` | 한 번의 공부 기록 분석 |
| Tutorbot 노드 | `#tutorbot` | Tutorbot이 만든 노드 식별에 사용 |
| 토픽 태그(topic tag, 주제 태그) | 예: `#python`, `#rust` | 목표·덤프·공부 기록을 연결하는 사용자 지정 태그 |

다음처럼 태그가 없는 묶음 노드를 만들어 그 아래에 목표·덤프·공부 항목을 각각 둘 수 있습니다.

```text
Python 학습                    ← 태그 없는 묶음 노드
  #목표 #python 업무 자동화에 필요한 Python 기초를 익힌다
  #지식덤프 #python 리스트와 튜플에 대해 현재 알고 있는 내용
  #공부 #python 오늘 공부한 내용을 기록한다
```

`Python 학습`처럼 태그가 없는 묶음 노드는 있어도 됩니다. 다만 `#목표` 노드 안에 `#공부` 노드를 넣는 식으로 학습 유형 노드를 서로 중첩하지 마세요. Tutorbot은 바깥 학습 항목의 하위 내용을 한 항목의 원문으로 읽으며, 내부의 다른 학습 유형 태그를 별도 항목으로 분류하지 않습니다.

태그는 본문에 붙이고, 뒤에 사람이 읽을 제목이나 설명을 씁니다. 예를 들어 `#공부 #python 딕셔너리의 키와 값을 학습했다`에서 `#공부`는 항목 종류, `#python`은 주제, 나머지는 본문입니다. 태그 이름은 대소문자를 구분하지 않습니다.

### 1) 목표 작성 예시

목표에는 “무엇을 할 수 있게 될지”를 구체적으로 적습니다. 주제 태그는 반드시 하나 이상 붙이세요.

```text
#목표 #python 업무용 CSV를 정리하고 반복 보고를 자동화하는 Python 스크립트를 작성한다
  현재 수준: 변수, 조건문, 반복문의 기본 문법은 알고 있다.
  완료 기준: CSV 파일을 읽어 필요한 행을 걸러내고 결과 파일로 저장하는 스크립트를 혼자 작성한다.
  사용 환경: Python 3, 로컬 파일
  목표 기한: 2027-01-31
```

목표의 자식 노드와 메모도 목표 원문에 포함되어 커리큘럼 생성에 전달됩니다. 실제 `tutorbot run`을 실행하면 목표 아래에 Tutorbot이 커리큘럼을 작성합니다. `#목표`만 쓰거나 주제 태그를 빼면 목표가 처리되지 않고 태그를 추가하라는 경고가 생성될 수 있습니다.

**목표가 여러 개라면** 각 목표에 서로 다른 주제 태그를 붙이고, 덤프와 공부 기록에도 대응하는 태그를 붙이세요.

```text
#목표 #python 업무 자동화 도구를 만든다
#목표 #rust 작은 명령줄 프로그램을 만든다

#공부 #python CSV 읽기와 쓰기를 연습했다
#공부 #rust 소유권과 참조의 차이를 공부했다
```

Dynalist에서 다음 경고가 나오면, 해당 `#공부` 또는 `#지식덤프` 노드의 **본문에** 연결할 목표와 같은 토픽 태그를 붙이세요.

```text
🤖 ⚠️ topic tag required when several goals are active #tutorbot
```

예를 들어 `#목표 #python ...`과 `#목표 #rust ...`가 있다면 `#공부`에는 `#python` 또는 `#rust`를, 덤프에도 연결할 쪽의 태그를 넣습니다. 태그는 노트나 자식 노드가 아니라 `#공부` / `#지식덤프`가 적힌 바로 그 노드의 본문에 써야 합니다. 태그를 추가한 뒤 `tutorbot run`을 다시 실행하면 해당 기록이 목표에 연결되어 처리됩니다. 활성 목표가 하나뿐이면 공부 기록과 덤프는 자동으로 그 목표에 연결되므로 토픽 태그가 필수는 아닙니다.

태그를 고친 뒤에도 이미 만들어진 경고 노드가 남아 있을 수 있습니다. 기록이 정상 처리되는 것을 확인한 다음, 오래된 경고 노드만 직접 삭제해도 됩니다.

### 2) 지식 덤프 예시

`#지식덤프`에는 지금까지 알고 있는 내용을 자신의 말로 적습니다. 짧은 주제명만 적기보다 원리, 예시, 알고 있는 범위와 헷갈리는 점을 함께 쓰면 평가에 쓸 근거가 분명해집니다.

덤프를 평가하려면 연결할 목표와 그 목표의 커리큘럼이 필요합니다. 먼저 목표를 작성하고 실제 `tutorbot run`으로 커리큘럼을 생성한 다음 덤프를 추가하는 순서를 권장합니다.

```text
#지식덤프 #python Python의 리스트와 튜플에 대해 내가 알고 있는 내용
  리스트는 여러 값을 순서대로 저장하고, 만든 뒤에도 원소를 바꿀 수 있다.
  튜플도 순서가 있는 여러 값을 저장하지만, 만든 뒤에는 원소를 바꿀 수 없다.
  예: 점의 좌표처럼 바뀌지 않아야 하는 값은 튜플로 표현할 수 있다.
  아직 잘 모르겠는 점: 리스트를 튜플 안에 넣었을 때 내부 리스트를 수정할 수 있는지 헷갈린다.
```

실행하면 Tutorbot은 덤프를 연결된 목표의 커리큘럼 개념과 비교하고, 내용을 사실이라고 전제하지 않고 평가합니다. 평가 요약, 명확한 오개념의 주장·정정·이유, 확인이 더 필요한 주장, 실제로 바뀐 개념 상태, 보완할 점과 다음 학습 추천을 덤프 노드의 Tutorbot 자식 노드에 기록합니다. 덤프 내용을 수정해 다시 평가하면 기존 평가 자식 노드를 갱신합니다. 확실히 판단하기 어려운 내용은 틀렸다고 단정하지 않고 `확인 필요`로 표시합니다.

예를 들어 “여러 가변 참조를 동시에 사용할 수 있다”처럼 잘못된 내용을 적으면, Tutorbot은 가능하면 정정 이유를 함께 적고 그 개념의 상태를 조정합니다. 덤프 평가만으로 올랐던 상태는 낮아질 수 있지만, 공부 기록이나 퀴즈 등 다른 근거가 있는 상태는 기존 전이 규칙에 따라 보호될 수 있습니다. Tutorbot은 원래 덤프 문장을 고치지 않으며, 평가와 커리큘럼 상태 변경을 별도 자식 노드로 남깁니다.

근거가 분명한 이해 상태를 평가하므로, “리스트를 공부했다”처럼 제목만 쓰기보다 실제로 이해한 내용을 적으세요. 목표가 여러 개면 `#python` 같은 주제 태그가 있어야 올바른 목표에 연결됩니다.

### 3) 오늘 공부한 내용 작성 예시

`#공부`에는 한 번의 학습에서 무엇을 읽거나 시도했고, 무엇을 이해했으며, 어디서 막혔는지 적습니다. 자식 노드에는 긴 예시나 생각의 단계를 나누어 쓸 수 있습니다.

```text
#공부 #python 딕셔너리의 키로 값을 찾고 갱신하는 방법을 연습했다.
  배운 점: dict[key]로 값을 읽고, dict[key] = value로 값을 추가하거나 바꾼다.
  직접 해본 예제: scores = {"민수": 80}에서 scores["민수"] = 90으로 점수를 갱신했다.
  결과: 출력값이 90으로 바뀌는 것을 확인했다.
  질문: 없는 키를 dict[key]로 읽으면 왜 KeyError가 나는지 더 알아보고 싶다.
```

#### `#공부` 피드백과 진도 반영 시점

`#공부`는 Tutorbot의 분석 대상입니다. 처리가 완료되면 공부 노드 아래에 개념 매핑, 교정·보완점, 다음 학습 내용 등의 피드백을 기록하고, 조건에 맞으면 복습 퀴즈 카드도 만듭니다. 커리큘럼 상태가 실제로 바뀐 경우에는 다음 진도 갱신에서 커리큘럼 노드와 진도율도 업데이트합니다.

기본 설정에서는 태그를 제외한 본문과 자식 노드의 합이 20자 이상이어야 하고, 해당 노드와 자식 노드 중 **가장 최근 수정 시각으로부터 60분**이 지나야 분석합니다. 이는 기록을 작성하는 도중에 너무 일찍 분석하지 않기 위한 대기 시간입니다. 따라서 기록을 막 작성하고 바로 `tutorbot run`을 실행하면 이번 실행에는 피드백이 없을 수 있습니다. 다시 실행해도 마지막 수정으로부터 60분이 지나기 전이면 계속 대기합니다.

로그에 `study.processed=0`과 `study.deferred_settle=1`이 나오면 공부 기록 하나를 인식했지만 정착 대기 때문에 아직 분석하지 않았다는 뜻입니다. 이는 `#공부` 태그를 무시했다는 뜻이 아닙니다. 마지막 수정 후 60분이 지난 다음 `tutorbot run`을 실행하세요. 기록을 수정하면 대기 시간도 다시 시작됩니다.

분석됐다고 해서 진도율이 반드시 오르는 것은 아닙니다. Tutorbot이 내용을 어떤 개념과 연결했는지, 이해 범위를 `mention`, `partial`, `full` 중 어떻게 평가했는지에 따라 상태 변경이 결정됩니다. 단순 언급(`mention`)은 상태를 올리지 않고, 부분 이해(`partial`)는 개념 상태를 최대 `partial`로 올립니다. `full`로 다루었고 이해가 확인된 경우에는 `understood`가 될 수 있습니다. 커리큘럼 가지의 `0/2` 표시는 두 하위 개념 중 `understood` 또는 `mastered`인 개념의 수이므로, `partial`만으로는 이 숫자가 오르지 않습니다. 전체 진도율 계산에서는 `partial`을 절반으로 반영합니다.

작업 완료를 진도에 반영하고 싶다면 “설치했다” 또는 “사용할 예정이다”만 적기보다 실제 수행한 작업, 확인한 결과, 이해한 내용을 구분해서 적으세요. 아직 할 예정인 작업은 학습 완료 내용과 섞지 말고 다음 계획이라고 표시하는 편이 정확합니다. 날짜를 직접 지정하려면 본문이나 메모에 `!(2026-11-14)`처럼 적을 수 있습니다.

### 목표·덤프·공부 기록의 차이

| 종류 | 무엇을 적나 | Tutorbot이 하는 일 |
|---|---|---|
| `#목표` | 앞으로 할 수 있게 되고 싶은 것 | LLM으로 목표별 커리큘럼을 생성 |
| `#지식덤프` | 이미 알고 있는 것과 이해의 근거 | 커리큘럼 개념에 대한 이해 상태를 평가 |
| `#공부` | 특정 학습 시간에 읽고·시도하고·이해한 것 | 개념 매핑, 피드백, 복습 카드 생성 |

- `#목표`에는 주제 태그가 필수입니다. `#공부`와 `#지식덤프`는 활성 목표가 하나일 때 생략할 수 있지만, 여러 목표가 있으면 해당 목표와 같은 주제 태그를 붙이세요.
- 태그는 반드시 노드 본문에 적으세요. 태그를 메모에만 적으면 항목으로 인식되지 않습니다. 단, 날짜 표기 `!(YYYY-MM-DD)`는 본문 또는 메모에서 인식합니다.
- 노트와 자식 노드의 텍스트도 목표·덤프·공부 원문에 포함됩니다. 태그가 없는 노드 아래에 자식으로 내용을 나누어 적으면 됩니다.

Tutorbot이 만든 노드는 `#tutorbot` 태그나 내부 마커로 식별됩니다. Tutorbot은 입력 문서를 읽고 목표별 커리큘럼, 진도, 피드백, 복습 퀴즈 등을 Dynalist에 기록합니다.

퀴즈에 답하려면 Dynalist에서 퀴즈 노드의 자식 노드로 답을 추가한 뒤 `tutorbot run`을 다시 실행합니다. `?`, `모름`, `pass`, `패스`는 모름/건너뛰기 답으로 처리됩니다.

## 4. 기본 실행 순서

아래 명령들은 모두 **터미널에서**, `tutor_ws` 프로젝트 루트와 활성화된 `.venv` 환경에서 실행합니다.

### 데이터베이스 초기화

```bash
tutorbot init-db
```

SQLite 데이터베이스를 생성하거나 필요한 스키마 마이그레이션을 적용합니다. 일반 실행에서도 마이그레이션이 수행되므로 필수 단계는 아닙니다.

### Dynalist 연결 확인

```bash
tutorbot doctor
```

설정된 문서 목록을 조회하고 문서 내용을 읽는 읽기 전용 검사입니다. 성공하면 문서별 노드 수와 버전을 출력합니다. 이 명령은 LLM 호출을 검사하지 않습니다.

`--write-test`는 Dynalist 문서에 테스트 노드를 만들고 수정한 다음 삭제하며, Gemini 호출도 검사합니다.

```bash
tutorbot doctor --write-test
```

이 옵션은 실제 문서를 수정합니다. 검사가 성공하면 Tutorbot이 테스트 노드를 삭제하지만, 중간에 실패하면 테스트 노드가 남을 수 있으므로 필요한 경우에만 사용하세요.

### 안전한 미리 실행

```bash
tutorbot run --dry-run
```

실제 Dynalist 문서를 읽어 파이프라인을 실행하지만 Dynalist에는 쓰지 않습니다. 기존 SQLite DB를 임시 DB로 복사해 사용하므로 결과도 실제 DB에 저장되지 않습니다. 단, `--fake-llm`을 지정하지 않으면 실제 Gemini API를 호출할 수 있어 토큰 사용량이 발생합니다.

외부 LLM 호출 없이 파이프라인을 점검하려면 다음처럼 실행합니다.

```bash
tutorbot run --dry-run --fake-llm
```

`--fake-llm`은 미리 정해진 테스트 응답을 사용합니다. `--dry-run` 없이 사용하면 테스트용 내용이 실제 Dynalist 문서에 기록될 수 있으므로 두 옵션을 함께 사용하는 것을 권장합니다.

### 실제 실행

```bash
tutorbot run
```

기본 설정의 Dynalist 문서를 읽고 필요한 분석을 수행한 뒤, 생성·수정할 내용을 실제 Dynalist에 씁니다. 실행 전에 SQLite DB를 `data/backup/`에 백업합니다(최대 7개 보관). 실제 Gemini API 키가 필요합니다.

특정 배치 날짜로 실행할 수도 있습니다.

```bash
tutorbot run --date 2026-11-14
```

`--date`는 배치 날짜를 지정하며, Dynalist에서 공부 항목의 작성 날짜를 직접 변경하지는 않습니다.

`run` 명령은 인자 및 설정을 읽기 전에 기본 `logs/tutorbot.log`에 실행 시작 기록을 남기므로, 그 단계에서 오류가 나도 실행 여부를 확인할 수 있습니다. 설정을 정상적으로 읽은 뒤의 실행 통계·경고·오류는 `[logging]` 설정의 로그 파일에 기록됩니다. 기본 위치는 프로젝트 폴더의 `logs/tutorbot.log`이며, 실행할 때마다 기존 파일에 이어 씁니다. 터미널에는 JSON 대신 실행 ID, 날짜, 상태, 로그 파일 위치가 간단히 표시됩니다.

로그 파일 위치를 바꾸려면 `config.toml`에 다음 설정을 추가하세요.

```toml
[logging]
log_file = "logs/tutorbot.log"
```

### 실행 통계

```bash
tutorbot stats
```

최근 실행 기록과 작업별 Gemini 호출 및 토큰 통계를 JSON으로 출력합니다.

## 5. 자주 확인할 사항

- `DYNALIST_TOKEN`이 없다는 오류가 나면 `.env` 또는 셸 환경변수를 확인하세요.
- Dynalist 문서가 조회되지 않으면 `config.toml`의 `file_ids`가 올바른지, 해당 API 토큰에 문서 접근 권한이 있는지 확인하세요.
- 실제 `run`에서 LLM 키 오류가 나면 `LLM_API_KEY`와 `[llm]` 설정을 확인하세요. `doctor` 기본 실행은 LLM 키를 확인하지 않습니다.
- `--dry-run`은 Dynalist 쓰기와 실제 DB 변경을 막지만, 기본 설정에서는 실제 LLM API 호출까지 막지는 않습니다.
- 현재 CLI에는 매일 자동 실행 기능이 없습니다. 정기 실행이 필요하면 외부 cron 또는 systemd timer에서 `tutorbot run`을 호출하도록 별도로 설정해야 합니다.

최신 Gemini 요청 제한·오류 재시도 정책은 [spec_v0.4.md](./specs/spec_v0.4.md)를, 다중 도메인 기획은 [spec_v0.3.md](./specs/spec_v0.3.md)를, 기존 학습 상세 명세는 [spec_v0.2.md](./specs/spec_v0.2.md)를 참고하세요.
