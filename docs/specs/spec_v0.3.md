# TutorBot 다중 도메인 확장 프로그램 명세서 초안 v0.3

## 1. 목표 및 범위

### 1.1 목표

기존 TutorBot의 학습 기능을 유지하면서 업무, 일상, 커리어, 개인 과업에서도 사용자의 기록을 읽고 분야별 규칙에 따라 피드백하는 구조를 제공한다.

공용 엔진은 기록 수집, 변경 감지, LLM 호출, 결과 검증, 피드백 쓰기, 재시도 및 멱등성을 담당한다. 각 도메인 프로필은 입력 문서, 태그, 분석 규칙, 프롬프트, 출력 형식을 정의한다.

기본 흐름은 다음과 같다.

> 도메인별 Dynalist 기록 수집 → 도메인 규칙에 따른 분석 → 피드백 생성 → 해당 도메인 문서에 기록

### 1.2 용어

| 용어 | 의미 |
|---|---|
| 도메인 | 학습, 업무, 일상, 커리어, 개인 과업처럼 봇을 적용하는 분야 |
| 도메인 프로필 | 문서, 태그, 규칙, 프롬프트, 출력 형식을 묶은 분야별 설정 |
| 추적 항목 | 진행을 추적하고 피드백을 받을 대상 |
| 분류 노드 | 추적 항목을 사용자가 묶기 위해 만든 부모 노드. 그 자체로는 추적 대상이 아님 |
| 진행 기록 | 추적 항목의 직접 자식으로 추가하는 날짜가 있는 작업 기록 |
| 상세 기록 | 진행 기록의 노트 및 자손 노드에 적는 구체적인 내용 |

### 1.3 1단계 범위

- 기존 학습 도메인의 기능과 동작을 유지한다.
- 업무, 일상, 커리어, 개인 과업 도메인을 추가한다.
- 각 도메인의 입력 문서를 지정하고 피드백은 같은 도메인 문서에 기록한다.
- 개인 과업의 칸반 상태, 추적 항목, 재귀적 진행 기록, 완료 분류 정보를 처리한다.
- 기존 SQLite 저장소를 실행 상태, 변경 이력, 멱등성, 완료 이벤트 저장에 재사용한다.
- 신규 통합 리포트, PDF 발행, 텔레그램·슬랙 연동은 1단계에서 구현하지 않는다. 후속 기능에 필요한 완료 이벤트와 분류 경로는 보존한다.

### 1.4 비목표

- 학습 도메인의 기존 규칙을 신규 도메인 규칙으로 대체하는 것
- LLM이 명시되지 않은 추적 항목, 완료 상태, 가족 일정 또는 날짜를 추측하는 것
- 1단계에서 채팅 서비스를 실시간 인터페이스로 제공하는 것
- 1단계에서 별도의 데이터베이스 제품을 도입하는 것

## 2. 공용 엔진과 도메인 프로필

### 2.1 공용 엔진 책임

1. 활성 도메인 프로필과 문서 설정을 읽는다.
2. 도메인별 Dynalist 문서를 읽고 트리 구조를 구성한다.
3. 태그, 상태, 분류, 기록 및 변경 여부를 파싱한다.
4. 도메인별 분석기를 호출하고 LLM 결과를 검증한다.
5. 처리 결과와 Dynalist 쓰기 작업을 DB에 안전하게 저장한다.
6. 도메인별 입력 문서에 피드백을 반영한다.
7. 오류, 재시도, 비용, 처리 통계를 기록한다.

공용 엔진은 도메인별 평가 의미를 직접 결정하지 않는다. 평가 기준은 프로필 및 해당 도메인의 처리 모듈이 제공한다.

### 2.2 도메인별 동작

| 도메인 ID | 입력 및 평가 목적 | 피드백 위치 |
|---|---|---|
| `study` | 기존 목표, 지식 덤프, 공부 기록, 퀴즈 및 진도 처리 | 기존 학습 문서 |
| `work` | 업무 목표 기여도, 진행 상황, 결과 및 더 효율적인 접근 평가 | 업무 문서 |
| `life` | 삶의 흐름과 가족 관련 과거·예정 이벤트 정리, 준비할 일 제안. 생산성 목표 평가를 하지 않음 | 일상 문서 |
| `career` | 설정된 업무·일상 기록에서 커리어 방향성을 근거와 함께 가설로 탐색 | 커리어 문서 |
| `personal_tasks` | 회사 업무와 분리된 개인 과업의 목표, 진행 및 효율성 평가 | 개인 과업 문서 |

커리어 도메인은 별도의 일일 기록을 요구하지 않는다. 업무·일상 기록을 입력으로 사용하고, 커리어 문서를 방향성 관찰 및 피드백의 축적·수정 장소로 사용한다. 분석 가능한 출처 도메인은 설정으로 제한한다.

### 2.3 공통 처리 규칙

- 각 프로필은 입력 문서를 하나 이상 지정할 수 있다.
- 피드백은 처리 대상 도메인의 문서에 쓴다. 커리어 분석은 업무·일상 문서를 읽을 수 있지만 결과는 커리어 문서에 쓴다.
- 노드 참조는 Dynalist 문서 ID와 노드 ID의 복합 키로 한다.
- 재실행 시 동일한 입력으로 중복 피드백 또는 완료 이벤트를 만들지 않는다.
- 사용자 노드를 임의로 삭제하거나 분류를 재배치하지 않는다.

## 3. 도메인별 규칙

### 3.1 학습

현재 TutorBot의 학습 기능을 회귀 기준으로 삼는다. 목표·덤프·공부 기록, 태그 분류, 퀴즈, SRS, 진도, 피드백, 기존 주간 리포트의 기존 동작을 확장 때문에 변경하지 않는다. 학습 프로필은 현행 설정을 호환하여 사용한다.

### 3.2 업무

- 업무 기록과 명시된 목표의 관계를 평가한다.
- 목표 달성에 기여한 활동, 진행 상황, 비효율 또는 대안이 될 수 있는 방법을 피드백한다.
- 개인 과업과 별도 프로필 및 문서를 사용한다.

### 3.3 일상

- 생산성이나 목표 달성도를 기준으로 일상을 평가하지 않는다.
- 기록을 바탕으로 삶의 흐름과 가족 관련 과거·예정 이벤트를 정리한다.
- 기록에 명시된 예정 이벤트가 있으면 미리 준비할 수 있는 사항을 제안한다.
- 날짜가 없거나 모호한 이벤트는 날짜를 임의로 지정하지 않는다.

### 3.4 커리어

- 매일 별도의 커리어 기록을 입력하도록 요구하지 않는다.
- 설정된 업무·일상 기록에서 커리어와 관련된 관심, 경험, 가치, 방향성의 단서를 찾는다.
- 추론은 확정된 사실이 아닌 가설로 표현하고 관찰 근거를 제시한다.
- 사용자가 방향성 가설이나 요약을 수정·정정할 수 있도록 커리어 문서에 기록한다.
- 설정되지 않은 도메인의 문서를 커리어 분석 입력으로 사용하지 않는다.

### 3.5 개인 과업 및 칸반

개인 과업은 회사와 무관하게 사용자가 해내려는 프로젝트, 단발성 일, 꾸준히 수행할 일, 하고 싶은 일, 1시간 이내 처리할 일 등을 포함한다. 업무와 같은 추적·피드백 틀을 사용하되 별도 문서와 프로필로 분리한다.

#### 칸반 상태명

상태 노드 이름은 PascalCase로 통일한다.

| 상태 노드 | 처리 규칙 |
|---|---|
| `Backlog` | 아직 중점 수행 대상이 아니더라도 진행 기록이 있으면 처리한다. |
| `InProgress` | 진행 중인 항목으로 분석하고 다음 행동을 제안한다. |
| `FastTrack` | 빠른 처리가 필요한 항목으로 보고 짧고 즉시 실행 가능한 피드백을 우선한다. |
| `Completed` | 완료 이벤트를 기록하고 최종 성과·회고를 남긴 뒤 일반 진행 피드백을 중단한다. |
| `Abandon` | 중단 상태를 기록하고 일반 진행 피드백을 중단한다. |

상태는 추적 항목의 조상 중 하나인 상태 노드로 판별한다. 상태 이동은 추적 항목의 동일성을 바꾸지 않는다. 상태 노드가 없거나 한 항목이 서로 충돌하는 상태 노드 아래에 있으면 임의로 상태를 정하지 않고 진단에 기록한다.

#### 추적 항목과 분류 노드

- 추적 항목 노드 자신에게 `#Track`이 있을 때만 추적 대상으로 등록한다.
- `해내고 싶은 프로젝트` 같은 부모 노드는 분류 노드이며, `#Track`이 없는 한 추적하지 않는다.
- 태그 없는 노드를 LLM이 추적 항목으로 추측하지 않는다.
- 추적 항목의 자식은 진행 기록으로 처리한다. 그 아래 자손은 상세 기록으로 처리한다.
- 자손 노드에 별도로 `#Track`이 붙으면 독립 추적 항목으로 처리한다.

#### 완료 분류

`Completed` 아래에는 완료 항목의 분류 노드를 둘 수 있다. 다음은 현재 정의된 분류명이며, 분류 노드 자체는 추적 항목이 아니다.

- 사회생활
- 소비
- 취미 등 하고 싶어서 해 본거
- 신변정리 관련
- 가정, 생활관련
- 애들 관련
- 회사관련
- 사업관련
- 커리어 관련

완료 이벤트에는 항목 식별자, 완료 시점, `Completed` 아래의 분류 경로를 저장한다. 후속 리포트는 이를 이용해 “이번 기간에 어떤 분류의 완료 항목이 추가되었는지” 요약할 수 있어야 한다.

## 4. 입력 인터페이스와 데이터 구조

### 4.1 추적 항목 구조

예시:

```text
Backlog
└─ 해내고 싶은 프로젝트
   └─ 내 이력서 포트폴리오 자료 작성 (56시간) #Track
```

`해내고 싶은 프로젝트`는 사용자 분류 노드이고, `#Track`이 붙은 자식만 추적 항목이다. 괄호 안의 예상 시간은 제목 텍스트이며, 별도 구조화된 시간 값으로 정의하지 않는 한 자동으로 계획·실적 시간으로 취급하지 않는다.

### 4.2 진행 기록 형식

새 기록은 추적 항목의 **직접 자식 노드**로 추가한다. 본문에는 간결한 수행 내용과 날짜를 `!(yyyy-mm-dd)` 형식으로 기록한다. 구체적인 설명은 해당 노드의 노트에 기록하고, 내용이 길거나 세부 분류가 필요하면 그 노드의 자식 노드에 기록한다.

```text
내 이력서 포트폴리오 자료 작성 (56시간) #Track
└─ 경력 기술서 초안 작성 !(2026-11-14)
   노트: 프로젝트별 역할과 성과를 정리함
   └─ 프로젝트 A
      └─ 담당 업무와 결과 정리
```

처리 시 직접 자식 기록뿐 아니라 각 기록의 노트와 모든 자손 노드를 재귀적으로 읽는다. 트리 경로를 보존해 상세 내용이 어느 진행 기록에 속하는지 식별한다. 진행 기록 하나의 자손은 그 진행 기록의 상세 내용이며, 별도 `#Track` 노드만 추적 항목 경계로 분리한다.

본문에서 유효한 날짜 표식 `!(yyyy-mm-dd)`를 파싱한다. 누락되거나 유효하지 않은 날짜는 LLM으로 추측하거나 자동 보정하지 않는다. 해당 기록 내용은 정성적 분석 문맥으로 사용할 수 있지만 날짜 기반 집계에서는 제외하고 실행 진단에 경고한다.

### 4.3 도메인 프로필 설정 예시

아래는 설정 개념을 설명하기 위한 예시이며, 기존 `config.toml`의 실 스키마와 합쳐 구현 시 검증한다.

```toml
[domains.study]
file_ids = ["<study document id>"]

[domains.work]
file_ids = ["<work document id>"]

[domains.life]
file_ids = ["<life document id>"]

[domains.career]
file_ids = ["<career document id>"]
source_domains = ["work", "life"]

[domains.personal_tasks]
file_ids = ["<personal tasks document id>"]
tracking_tag = "Track"
status_nodes = ["Backlog", "InProgress", "Abandon", "Completed", "FastTrack"]
```

각 프로필은 활성화 여부, 문서 ID, 태그 별칭, 규칙·프롬프트를 지정할 수 있다. 기존 전역 학습 설정을 사용하는 사용자는 이를 학습 프로필로 읽는 호환 경로를 제공한다. 비밀 토큰은 기존 원칙대로 환경 변수에서만 읽는다.

### 4.4 저장할 상태

기존 SQLite DB와 outbox 구조를 재사용한다. 구현 시 필요한 논리 데이터는 다음과 같다.

| 데이터 | 주요 필드 |
|---|---|
| 도메인 처리 상태 | `domain_id`, 문서 ID, 노드 ID, 마지막 처리 해시, 처리 상태 |
| 진행 기록 상태 | 추적 항목 ID, 기록 노드 ID, 날짜 원문/정규화 날짜, 하위 트리 해시 |
| 완료 이벤트 | 항목 복합 키, 상태 전이 식별자, 관찰/완료 시점, 완료 분류 경로 |
| 도메인 실행 상태 | 실행 ID, 도메인 ID, 처리 결과, 오류 및 재시도 정보 |

구체적인 테이블과 마이그레이션은 현재 스키마 및 outbox와 중복되지 않도록 설계한다. 완료 이벤트는 동일한 상태 전이에 대해 중복 생성되지 않아야 한다.

## 5. 처리 및 출력 규칙

### 5.1 배치

기존 일일 배치에서 활성 도메인을 처리한다. 도메인별 문서 읽기와 분석 실패는 다른 도메인 처리를 불필요하게 중단시키지 않는다. 모든 문서 읽기가 실패하는 경우에는 해당 배치를 실패로 표시한다.

LLM 호출은 DB 트랜잭션 밖에서 수행한다. 검증된 결과, 실행 상태, Dynalist 쓰기 작업은 기존 outbox의 원자성 및 재시도 규칙을 따른다.

### 5.2 출력 위치

피드백은 분석 대상 도메인의 입력 문서에 기록한다. 커리어 분석은 업무·일상 문서를 입력으로 참조하더라도 커리어 문서에만 결과를 기록한다. 봇이 만든 노드는 기존 TutorBot의 식별 및 멱등성 규칙을 따른다.

### 5.3 완료 이벤트 처리

- 상태가 `Completed`로 바뀐 시점에 완료 이벤트를 기록한다.
- 동일 항목과 동일 완료 전이에 대한 재실행은 중복 이벤트를 만들지 않는다.
- 완료 상태에서 다른 상태로 이동한 뒤 다시 완료된 경우는 새로운 완료 전이로 기록한다.
- 완료 분류는 `Completed` 아래에서 항목으로 이어지는 경로를 저장한다.
- 최초 실행 시 이미 `Completed` 아래에 있는 항목은 실제 완료 시점을 알 수 없으므로 최초 발견 시점과 실제 완료 시점을 혼동하지 않는다. 확인할 수 없는 완료 시점은 추정하지 않는다.

## 6. 단계별 구현 계획

### 1단계: 도메인 확장

- 학습 기능의 회귀 없이 도메인 프로필을 도입한다.
- 업무·일상·커리어·개인 과업을 추가한다.
- 개인 과업에서 PascalCase 칸반 상태, 명시적 `#Track`, 재귀적 상세 기록, 날짜 검증, 완료 분류 이벤트를 지원한다.
- 신규 통합 리포트는 구현하지 않지만 완료 이벤트와 분류 경로를 보존한다.

### 2단계: 리포트

- 주간·월간·분기·연간 리포트를 추가한다.
- 도메인별 요약과 개인 과업의 분류별 완료 항목을 제공한다.
- 일상 이벤트 및 커리어 방향성 요약은 근거가 있는 기록을 사용한다.
- 기존 학습 도메인의 주간 리포트는 유지한다.

### 3단계: PDF 발행

- 리포트를 필요 시 PDF로 발행한다.
- Dynalist 기록 기능과 PDF 생성을 분리한다.

### 4단계: 텔레그램·슬랙

- 리포트 전달을 지원한다.
- 사용자 커맨드를 받아 지정 도메인의 기록으로 반영한다.
- 입력 출처와 대상 도메인을 명확히 연결하고, 기존 DB/outbox의 신뢰성 규칙을 재사용한다.

## 8. 엣지 케이스 및 수용 기준

| 구분 | 수용 기준 |
|---|---|
| 기존 기능 보존 | 기존 학습 파이프라인 테스트 및 동작이 신규 프로필 도입 후에도 유지된다. |
| 도메인 분리 | 각 프로필의 문서·태그·규칙이 다른 도메인 처리에 섞이지 않는다. 피드백은 대상 도메인 문서에만 기록된다. |
| 커리어 출처 | 커리어 분석은 설정된 업무·일상 출처만 읽고 결과는 커리어 문서에 기록한다. |
| 추적 항목 구분 | `#Track`이 없는 분류 노드는 추적되지 않는다. LLM이 태그 누락만으로 대상을 생성하지 않는다. |
| Backlog 처리 | `Backlog` 아래의 추적 항목도 진행 기록이 바뀌면 처리된다. |
| 칸반 상태 | `InProgress`, `Backlog`, `Abandon`, `Completed`, `FastTrack`을 일관되게 판별하고 상태 이동 후에도 동일 항목으로 연결한다. |
| 재귀 기록 | 직접 자식 기록, 노트, 자손 노드가 빠짐없이 읽히고 부모 진행 기록과의 계층 관계가 유지된다. |
| 날짜 유효성 | 유효한 `!(yyyy-mm-dd)`만 날짜로 사용한다. 누락·잘못된 날짜를 추정하지 않고 진단에 표시하며 날짜 집계에서 제외한다. |
| 일상 이벤트 | 기록에 없는 가족 이벤트나 날짜를 만들어내지 않고, 일상 도메인을 업무식 목표 평가로 처리하지 않는다. |
| 완료 분류 | 완료 이벤트에 `Completed` 아래의 분류 경로가 저장되고, 재실행으로 동일 이벤트가 중복 생성되지 않는다. |
| 완료 시점 불명 | 최초 실행에서 이미 완료된 항목을 발견한 경우 실제 완료일을 발견일로 꾸며내지 않는다. |
| 오류 처리 | 문서·LLM 오류는 실행 기록과 진단에 드러나며, 성공 결과처럼 조용히 대체하지 않는다. |
| 범위 | 1단계에서는 기존 학습 리포트를 제외한 새 통합 리포트, PDF, 텔레그램·슬랙 기능을 구현하지 않는다. |
